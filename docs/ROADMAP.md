# План развития после пилота

> Обновление: пункт 3 (интеграция с AD) реализован — см.
> `printaudit/ad/`, `/admin/ad-users`, `/admin/ad-groups`. Ниже оставлены
> актуальные пункты и добавлены новые, вытекающие из этой ветки.

1. **Централизованный сбор с 4 объектов.**
   Схема уже готова к этому — каждая запись `print_jobs` несёт `site_code`,
   а уникальность обеспечена парой `(site_code, record_id)`, а не одним
   `record_id`. Варианты объединения:
   - каждый объект раз в сутки экспортирует новые строки в центральную
     PostgreSQL (простой Python-скрипт, читающий `print_jobs` где
     `created_at > последний_экспорт`);
   - либо все 4 сборщика с самого начала пишут в один центральный
     PostgreSQL по VPN (тогда SQLite на объектах не нужен вообще — меняется
     только `db.url` в `config.yaml`, код не трогается).

2. **Более точное определение цвета.**
   Сейчас цвет определяется по имени очереди печати (см.
   `docs/ADMIN_GUIDE.md`, раздел про разделение очередей). Более точные
   варианты на будущее: разбор EMF-спула задания (сложно и специфично для
   драйвера), либо WMI/SNMP-счётчики самого МФУ по цветным/ч.б. страницам
   (зависит от модели, снова упирается в вендора — то, что пилот сознательно
   обходит).

3. ~~**Интеграция с AD вместо CSV.**~~ Сделано — см. выше.

4. **Квоты и блокировки.**
   Windows Print Server не умеет нативно блокировать печать по лимиту —
   потребуется отдельный процесс, который periodически проверяет
   накопленный `cost`/`total_pages` пользователя и, при превышении, снимает
   ему право печати на очередь (`Set-Printer`/ACL) до начала следующего
   периода. Это отдельная и рискованная зона (легко случайно заблокировать
   всех) — делать отдельным пилотом.

5. **Алерты в Telegram/Email.**
   Простой периодический скрипт (тот же Task Scheduler) поверх
   `printaudit.queries`: сравнить накопленные `cost`/`pages` за период с
   порогом на пользователя/отдел из конфига и отправить сообщение через
   Telegram Bot API или SMTP при превышении.

6. **Активация AD-групп для правил "по расписанию".**
   Сейчас применение правил AD-группа→отдел (`/admin/department-rules`)
   требует ручного клика "Применить" после dry-run — осознанно, чтобы
   изменение отделов было видимым действием, а не тихим фоновым процессом.
   Если это станет неудобно на 4 объектах, можно добавить туда же Task
   Scheduler задачу, вызывающую `apply_ad_department_sync()` по расписанию —
   код для этого уже есть (`printaudit/department_resolver.py`), не хватает
   только обёртки-CLI и записи каждого автоприменения в `audit_log` с явной
   меткой "автоматически", чтобы не путать с ручными изменениями.

7. **Пагинация длинных списков в админке.**
   `/admin/ad-users` и `/admin/administrators` сейчас показывают полный
   список без пагинации — приемлемо для пилота (сотни, не тысячи записей),
   но при росте числа импортированных пользователей AD стоит добавить
   постраничную навигацию (`printaudit.queries`-подобный `limit`/`offset`
   уже используется для отчётов, для админки такого пока нет).

8. **Синхронизация AD по расписанию, а не только по кнопке.**
   `/admin/ad-users/resync` и обнаружение принтеров сейчас запускаются
   вручную из UI. Для 4 объектов может быть удобнее завести отдельную
   задачу Task Scheduler (по аналогии с `deploy/register_collector_task.ps1`)
   на пару раз в день, чтобы новые сотрудники/группы AD подтягивались
   без участия администратора.
