# Руководство администратора

## 1. Включить журнал печати на Print Server

Через PowerShell (от администратора):

```powershell
wevtutil set-log Microsoft-Windows-PrintService/Operational /enabled:true
```

Проверить, что журнал включён:

```powershell
Get-WinEvent -ListLog "Microsoft-Windows-PrintService/Operational" | Select LogName, IsEnabled, RecordCount
```

Альтернатива через GUI: Event Viewer → Applications and Services Logs →
Microsoft → Windows → PrintService → правый клик на "Operational" → Enable Log.

## 2. Проверить, что события 307 пишутся

1. Отправьте тестовый документ на печать через любую очередь этого сервера
   (обычной печатью с любого клиентского ПК — не напрямую на IP/USB).
2. Проверьте журнал:

```powershell
Get-WinEvent -LogName "Microsoft-Windows-PrintService/Operational" `
    -FilterXPath "*[System[EventID=307]]" -MaxEvents 5 | Format-List TimeCreated, Message
```

Если событие есть — журнал настроен верно, можно калибровать сборщик (шаг 3).
Если события нет — проверьте, что печать действительно проходит через очередь
именно этого сервера (Get-Printer / Get-PrintJob), а не напрямую на IP принтера.

## 3. Калибровка индексов полей (`collector.field_map`)

Индексы позиционных свойств события 307 не документированы Microsoft как
стабильные и могут отличаться между Windows Server 2016/2019/2022 и версией
драйвера принтера. **Это нужно проверить на каждом из 4 объектов** перед тем,
как доверять отчётам.

```powershell
cd C:\path\to\print-audit
.\collector\calibrate_event_fields.ps1
```

Скрипт печатает для нескольких последних событий 307 текст сообщения и
пронумерованный список всех свойств. Сопоставьте индекс с полем (Job Id, имя
документа, пользователь, имя принтера, число страниц) по смыслу значения и
поправьте `collector.field_map` в `config/config.yaml`:

```yaml
collector:
  field_map:
    job_id: 0
    document_name: 1
    user_name: 2
    printer_name: 4
    total_pages: 8
```

После правки запустите сборщик один раз вручную и проверьте `logs/collector.log`
и таблицу `print_jobs` — поля должны выглядеть осмысленно (имя пользователя,
реальное имя принтера, число страниц > 0). Если сборщик пишет предупреждения
`не удалось разобрать поля` или `field_map.<поле>=N вне диапазона` — индексы
ещё не откалиброваны верно: сообщение прямо называет проблемное поле и
показывает, сколько свойств реально пришло в событии, так что не нужно
угадывать вручную.

> **Известный случай.** На одном из реальных Windows Server total_pages
> оказался в `Properties[7]`, а не в `Properties[8]`, как в примере выше.
> Это не ошибка примера, которую один раз поправили и забыли — это
> подтверждение того, что индексы **обязательно нужно проверять на каждом
> объекте отдельно**: они зависят от версии Windows Server и версии
> драйвера принтера, а не только от версии Windows.

Если после калибровки `total_pages` в отчётах стабильно получаются нулевые
страницы или сборщик пишет `field_map.total_pages=N вне диапазона`,
попробуйте соседние индексы (в том числе 7) и сверяйте с `Message` того же
события в выводе `calibrate_event_fields.ps1` — там число напечатанных
страниц обычно указано словами ("Pages printed: N" / "Распечатано страниц: N").

## 4. Разделение очередей Ч/Б и цвет (рекомендация)

Событие 307 не сообщает, был ли конкретный документ цветным. Самый простой и
надёжный способ получить корректный учёт стоимости — завести на печатном
сервере **две очереди на одно и то же МФУ**: одну с принудительным Ч/Б-режимом
в настройках драйвера по умолчанию, вторую — цветную, и назвать их так, чтобы
они однозначно матчились в `price_list` (например, `HP-3F-BW` и `HP-3F-Color`).
Пользователи выбирают нужную очередь при печати. Это не костыль — так делают
многие организации именно из-за отсутствия цвета в событии 307.

Если это неприемлемо, оставьте одну очередь и одно тарифное правило на
принтер (менее точно, но проще для пользователей) — см. `price_list` ниже.

## 5. Добавить/изменить принтер

Ничего настраивать в проекте не нужно — как только на сервере появляется
новая очередь печати и через неё печатают, задания начинают попадать в
`print_jobs` автоматически (по имени очереди). При необходимости добавьте
для неё тарифное правило:

```sql
INSERT INTO price_list (printer_name_pattern, is_color, price_per_page, currency, priority)
VALUES ('HP-3F-Color*', 1, 40, 'KZT', 10);
```

(либо через любой SQLite-клиент — БД лежит в `data/print_audit.db`).
Правила проверяются по `priority` (по убыванию) — более конкретные паттерны
должны иметь больший приоритет, чем `*`.

## 6. Добавить отдел/пользователя

Отредактируйте `config/users_departments.csv`:

```csv
user_name,department_name,cost_center_code
DOMAIN\ivanov,Бухгалтерия,CC-100
```

и выполните:

```powershell
python scripts\sync_users_departments.py
```

Скрипт создаёт отсутствующие отделы, обновляет `department_id` пользователей
и пересчитывает `department_id` у уже накопленных заданий печати (чтобы
переезд сотрудника между отделами не искажал прошлые отчёты по текущей
структуре).

## 7. Логи

- Сборщик: `logs/collector.log` — одна строка на запуск (получено/вставлено/
  пропущено событий) плюс подробные предупреждения по каждой проблемной записи.
- Веб-UI: вывод `uvicorn` в консоли; при запуске как службы NSSM (см. ниже) —
  в файл, указанный в конфигурации службы.

## 8. Запуск веб-UI как службы Windows (опционально)

Для пилота достаточно `deploy\run_webapp.ps1`, запущенного вручную или через
Task Scheduler "при старте системы". Для постоянной работы без открытой
консоли — использовать [NSSM](https://nssm.cc/):

```powershell
nssm install PrintAuditWeb "C:\Python311\python.exe" ^
    "-m uvicorn webapp.main:app --host 0.0.0.0 --port 8000"
nssm set PrintAuditWeb AppDirectory "C:\path\to\print-audit"
nssm set PrintAuditWeb AppStdout "C:\path\to\print-audit\logs\web.log"
nssm set PrintAuditWeb AppStderr "C:\path\to\print-audit\logs\web.log"
nssm start PrintAuditWeb
```
