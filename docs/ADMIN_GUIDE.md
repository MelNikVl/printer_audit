# Руководство администратора

Разделы 1–4 — про сам сбор событий печати (не изменились с MVP). Разделы
5–6 обновлены под новую схему (принтеры/тарифы/отделы теперь управляются
через `/admin`, а не только SQL/CSV). Разделы 9+ — новые: провайдеры входа
(локальный + AD, оба независимо опциональны), настройка AD, bootstrap
superadmin (локальный и AD), разделы админки, тарифы, аудит, миграции, тесты.
Разделы 18–21 (новые) — построчный журнал заданий печати, режимы
standalone/agent/central, центральный менеджер Print Server и развёртывание
агента на площадке; подробное архитектурное описание — в отдельном
документе [docs/MULTISITE_ARCHITECTURE.md](MULTISITE_ARCHITECTURE.md).

## 1. Включить журнал печати на Print Server

Через PowerShell (от администратора):

```powershell
wevtutil set-log Microsoft-Windows-PrintService/Operational /enabled:true
```

Проверить, что журнал включён:

```powershell
Get-WinEvent -ListLog "Microsoft-Windows-PrintService/Operational" | Select LogName, IsEnabled, RecordCount
```

Альтернатива через GUI: Event Viewer → Applications and Services Logs →
Microsoft → Windows → PrintService → правый клик на "Operational" → Enable Log.

## 2. Проверить, что события 307 пишутся

1. Отправьте тестовый документ на печать через любую очередь этого сервера
   (обычной печатью с любого клиентского ПК — не напрямую на IP/USB).
2. Проверьте журнал:

```powershell
Get-WinEvent -LogName "Microsoft-Windows-PrintService/Operational" `
    -FilterXPath "*[System[EventID=307]]" -MaxEvents 5 | Format-List TimeCreated, Message
```

Если событие есть — журнал настроен верно, можно калибровать сборщик (шаг 3).
Если события нет — проверьте, что печать действительно проходит через очередь
именно этого сервера (Get-Printer / Get-PrintJob), а не напрямую на IP принтера.

## 3. Калибровка индексов полей (`collector.field_map`)

Индексы позиционных свойств события 307 не документированы Microsoft как
стабильные и могут отличаться между Windows Server 2016/2019/2022 и версией
драйвера принтера. **Это нужно проверить на каждом из 4 объектов** перед тем,
как доверять отчётам.

```powershell
cd C:\path\to\print-audit
.\collector\calibrate_event_fields.ps1
```

Скрипт печатает для нескольких последних событий 307 текст сообщения и
пронумерованный список всех свойств. Сопоставьте индекс с полем (Job Id, имя
документа, пользователь, имя принтера, число страниц) по смыслу значения и
поправьте `collector.field_map` в `config/config.yaml`:

```yaml
collector:
  field_map:
    job_id: 0
    document_name: 1
    user_name: 2
    printer_name: 4
    total_pages: 8
```

После правки запустите сборщик один раз вручную и проверьте `logs/collector.log`
и таблицу `print_jobs` — поля должны выглядеть осмысленно (имя пользователя,
реальное имя принтера, число страниц > 0). Если сборщик пишет предупреждения
`не удалось разобрать поля` или `field_map.<поле>=N вне диапазона` — индексы
ещё не откалиброваны верно: сообщение прямо называет проблемное поле и
показывает, сколько свойств реально пришло в событии, так что не нужно
угадывать вручную.

> **Известный случай.** На одном из реальных Windows Server total_pages
> оказался в `Properties[7]`, а не в `Properties[8]`, как в примере выше.
> Это не ошибка примера, которую один раз поправили и забыли — это
> подтверждение того, что индексы **обязательно нужно проверять на каждом
> объекте отдельно**: они зависят от версии Windows Server и версии
> драйвера принтера, а не только от версии Windows.

Если после калибровки `total_pages` в отчётах стабильно получаются нулевые
страницы или сборщик пишет `field_map.total_pages=N вне диапазона`,
попробуйте соседние индексы (в том числе 7) и сверяйте с `Message` того же
события в выводе `calibrate_event_fields.ps1` — там число напечатанных
страниц обычно указано словами ("Pages printed: N" / "Распечатано страниц: N").

## 4. Разделение очередей Ч/Б и цвет (рекомендация)

Событие 307 не сообщает, был ли конкретный документ цветным. Самый простой и
надёжный способ получить корректный учёт стоимости — завести на печатном
сервере **две очереди на одно и то же МФУ**: одну с принудительным Ч/Б-режимом
в настройках драйвера по умолчанию, вторую — цветную, и назвать их так, чтобы
они однозначно матчились в `price_list` (например, `HP-3F-BW` и `HP-3F-Color`).
Пользователи выбирают нужную очередь при печати. Это не костыль — так делают
многие организации именно из-за отсутствия цвета в событии 307.

Если это неприемлемо, оставьте одну очередь и одно тарифное правило на
принтер (менее точно, но проще для пользователей) — см. `price_list` ниже.

**Важно про то, что показывает журнал/отчёты.** Если очередь вообще никак
не настроена (ни `color_mode`, ни тариф, ни правило `price_list`), цвет
считается **достоверно неизвестным** и в журнале (`/print-jobs`) показывается
как «не определено», а не «Ч/б» — раньше это молча превращалось в «Ч/б»,
что было неверно и могло занижать реальную стоимость печати. Для расчёта
стоимости неопределённый цвет всё равно консервативно тарифицируется как
Ч/Б (пока вы не настроите очередь), но это решение о цене, а не заявление о
факте — подробности в [docs/MULTISITE_ARCHITECTURE.md](MULTISITE_ARCHITECTURE.md), §8.

## 5. Добавить/изменить принтер

Ничего настраивать в Windows не нужно — как только на сервере появляется
новая очередь печати и через неё печатают, коллектор сам заводит её в
`printer_queues` (как `discovered_by_collector`, неотконфигурированную).
Но чтобы она сразу нашлась и была видна ДО первой печати, а не только
постфактум, зайдите как admin/superadmin в **`/admin/printers`** и нажмите
«Обнаружить / синхронизировать очереди» — это вызывает `Get-Printer` и
подтягивает все локальные очереди сервера сразу.

На той же странице для каждой очереди можно задать:
- отображаемое имя;
- цвет (Ч/Б / цветной / неизвестно) — событие 307 сам цвет не сообщает, см.
  раздел 4 про разделение очередей;
- быстрый тариф (цена/страница) — без периода действия и приоритета;
- включён ли учёт для этой очереди (`collection_enabled` — выключить, если
  очередь тестовая/техническая и её не нужно тарифицировать).

Если нужен более сложный тариф (свой на период времени, с приоритетом
относительно других правил) — используйте **`/admin/pricing`** (см. раздел 13).
Исчезновение очереди из `Get-Printer` (например, принтер временно выключен)
помечает её "пропала", но НЕ удаляет ни саму очередь, ни историю печати по
ней — она снова станет активной при следующем обнаружении, если появится.

Легаси-таблица `price_list` (заполнялась SQL-запросами в MVP) продолжает
работать как fallback самого низкого приоритета — трогать её вручную больше
не нужно.

## 6. Отделы и пользователи

Основной путь — через Active Directory (раздел 10): импортировать
пользователей/группы в `/admin/ad-users` и `/admin/ad-groups`, связать
AD-группы с отделами. Для организаций без AD или как временный fallback
остаётся CSV-путь из MVP:

```csv
user_name,department_name,cost_center_code
DOMAIN\ivanov,Бухгалтерия,CC-100
```

```powershell
python scripts\sync_users_departments.py
```

Скрипт создаёт отсутствующие отделы, обновляет `department_id` пользователей
и пересчитывает `department_id` у уже накопленных заданий печати. При
сопоставлении задания печати с отделом приоритет у AD (`ad_users`) —
CSV-таблица `users` используется только если пользователь не найден в
`ad_users` (см. `printaudit/department_resolver.py`).

## 7. Логи

- Сборщик: `logs/collector.log` — одна строка на запуск (получено/вставлено/
  пропущено событий) плюс подробные предупреждения по каждой проблемной записи.
- Веб-UI: вывод `uvicorn` в консоли; при запуске как службы NSSM (см. ниже) —
  в файл, указанный в конфигурации службы.

## 8. Запуск веб-UI как службы Windows (опционально)

Для пилота достаточно `deploy\run_webapp.ps1`, запущенного вручную или через
Task Scheduler "при старте системы". Для постоянной работы без открытой
консоли — использовать [NSSM](https://nssm.cc/):

```powershell
nssm install PrintAuditWeb "C:\path\to\print-audit\.venv\Scripts\python.exe" ^
    "-m uvicorn webapp.main:app --host 0.0.0.0 --port 8000"
nssm set PrintAuditWeb AppDirectory "C:\path\to\print-audit"
nssm set PrintAuditWeb AppStdout "C:\path\to\print-audit\logs\web.log"
nssm set PrintAuditWeb AppStderr "C:\path\to\print-audit\logs\web.log"
nssm start PrintAuditWeb
```

Как и у сборщика (см. `deploy/register_collector_task.ps1`), важно указать
Python именно из `.venv` проекта — системный/store `python.exe` не будет
иметь установленных зависимостей (fastapi, sqlalchemy, ldap3, ...).

## 9. Провайдеры входа: локальный и Active Directory

Приложение поддерживает два независимых способа входа одновременно:
локальные учётки (пароль — Argon2id-хэш в своей БД) и Active Directory. AD
полностью опционален — систему можно эксплуатировать вообще без AD, только
на локальных учётках, и наоборот.

Переключатели — `.env`:

```
LOCAL_AUTH_ENABLED=true
AD_AUTH_ENABLED=false
```

Если переменная отсутствует в `.env` вообще, код считает её `true` — так
апгрейд уже развёрнутого сервера, где AD уже настроен и используется, не
отключает его молча только потому, что в старом `.env` не было этой строки.
Реально AD доступен, только если `AD_AUTH_ENABLED=true` **и** заполнены
`AD_SERVER`/`AD_BASE_DN` (раздел 10) — одного флага недостаточно.

**Когда AD отключён (флагом или просто не настроен):**
- страница входа показывает только форму локального входа, без вкладки AD;
- `POST /login` с провайдером `ad` отклоняется сразу, без единого обращения
  к LDAP;
- разделы `/admin/administrators`, `/admin/ad-users`, `/admin/ad-groups`
  показывают нейтральное «AD отключён» вместо формы поиска — уже
  импортированные ранее AD-пользователи/группы остаются видны и
  редактируемы (отдел, блокировка и т.п.), но поиск/импорт/синхронизация
  недоступны;
- сама админка (отделы, принтеры, тарифы, отчёты, управление
  администраторами) работает полностью — эти разделы не зависят от AD.

**Локальные пароли:** хранятся только как Argon2id-хэш, минимум 12 символов,
после 5 неверных попыток подряд учётка временно блокируется на 15 минут (см.
`printaudit/security/local_auth.py` — это не настраивается через `.env` в
этом пилоте, при необходимости менять константы
`LOCKOUT_THRESHOLD`/`LOCKOUT_DURATION_MINUTES` в коде).

## 10. Active Directory: настройка и минимальные права

Все параметры AD берутся из переменных окружения / файла `.env` (см.
`.env.example`), а НЕ из `config.yaml` — этот файл никогда не коммитится и
не должен рассылаться вместе с кодом.

| Переменная | Назначение |
|---|---|
| `AD_SERVER` | адрес контроллера домена (например, `dc01.example.local`) |
| `AD_PORT` | 636 для LDAPS (рекомендуется), 389 для LDAP |
| `AD_USE_SSL` | `true` — включить LDAPS. **На проде должно быть `true`**: иначе пароль пользователя при входе идёт по сети в открытом виде |
| `AD_DOMAIN` | **DNS-имя домена / UPN suffix** (например `corp.example.local`) — см. предупреждение ниже, это НЕ NetBIOS-имя |
| `AD_BASE_DN` | базовый DN домена, например `DC=corp,DC=example,DC=local` |
| `AD_USER_SEARCH_BASE` / `AD_GROUP_SEARCH_BASE` | сузить поиск пользователей/групп до нужных OU (по умолчанию — весь `AD_BASE_DN`) |
| `AD_BIND_USER` / `AD_BIND_PASSWORD` | сервисный аккаунт для ПОИСКА (вход по логину/паролю самого пользователя не требует bind-аккаунта — проверяется прямым bind-ом от имени пользователя) |

### `AD_DOMAIN` — единственная модель, без вариантов

`AD_DOMAIN` используется для построения UPN при входе пользователя:
введённый логин сводится к `sam@AD_DOMAIN` (например, `ivanov@corp.example.local`)
**независимо** от того, в каком из трёх форматов (`DOMAIN\login` /
`login@domain` / `login`) он был введён в форму — то, что пользователь
указал как домен, при этом игнорируется. Тот же `AD_DOMAIN` используется для
нормализованного логина, который вы увидите в БД/аудите/UI — то есть
`corp.example.local\ivanov`, а не привычный `CORP\ivanov`. Это ожидаемо.

```
ПРАВИЛЬНО:   AD_DOMAIN=corp.example.local
НЕПРАВИЛЬНО: AD_DOMAIN=CORP
```

Значение вида `CORP` (короткое NetBIOS-имя без точек) — частая ошибка при
заполнении `.env` по памяти: с таким значением попытка входа реально
собирается в `ivanov@CORP`, что не является валидным UPN и почти наверняка
не пройдёт bind на настоящем AD. Отдельной переменной для NetBIOS-имени
(например, `AD_NETBIOS_DOMAIN`) в проекте нет и не требуется — код нигде не
использует NetBIOS-форму домена отдельно от того, что вводит пользователь
в форме логина (а её парсит и отбрасывает `printaudit/ad_normalize.py`, не
храня отдельно).

`AD_BIND_USER` — независимая от `AD_DOMAIN` строка, ldap3/AD принимают её
как есть: подходит UPN (`svc-printaudit@corp.example.local`, как в
`.env.example`) или полный DN. Down-level формат (`CORP\svc-printaudit`)
тоже технически работает с настоящим AD, но в примере намеренно показан
UPN — чтобы в одном файле не было двух разных нотаций домена одновременно.

**Минимальные права сервисного аккаунта** (`AD_BIND_USER`): обычный
пользователь домена без каких-либо административных прав, с правом читать
(на чтение — по умолчанию есть у любого аутентифицированного пользователя
домена в большинстве AD) атрибуты `sAMAccountName`, `userPrincipalName`,
`displayName`, `mail`, `objectSid`, `objectGUID`, `distinguishedName`,
`memberOf` в пределах `AD_USER_SEARCH_BASE`/`AD_GROUP_SEARCH_BASE`. Права
администратора домена НЕ нужны и не должны выдаваться — приложение не
пишет в AD ни в каком режиме.

Проверить настройки можно, попытавшись войти в веб-интерфейс под своим
логином — при неверном `AD_SERVER`/сертификате будет нейтральное сообщение
об ошибке связи с AD на странице входа (а не зависание и не подробности
исключения — полный текст ошибки уходит только в лог сервера, в UI — короткий ID для поиска по логу).

## 11. Bootstrap первого superadmin

Два варианта — через AD или полностью локально, независимо от того,
настроен AD или нет.

**AD-вариант** (пароли не хранятся вообще, вход проверяется через AD):

```powershell
.\.venv\Scripts\python.exe scripts\bootstrap_superadmin.py --login "DOMAIN\ivanov"
```

По умолчанию логин проверяется через AD (bind-аккаунт из `.env`) — команда
откажется выдать доступ логину, которого нет в AD (защита от опечатки).
Если AD пока не настроен (только для изолированного тестового стенда) —
флаг `--skip-ad-check` пропускает эту проверку, но тогда легко ошибиться в
логине, о чём скрипт явно предупреждает.

**Локальный вариант** (не требует AD вообще):

```powershell
.\.venv\Scripts\python.exe scripts\bootstrap_local_superadmin.py --login localadmin
```

Пароль спрашивается интерактивно через `getpass` дважды подряд (не
отображается на экране, не принимается аргументом командной строки —
аргумент вида `--password` этот скрипт не понимает в принципе, значение
пароля в истории шелла/списке процессов было бы виден любому другому
пользователю той же машины). Слабый пароль (короче 12 символов) или
несовпадение при повторном вводе — просто переспрашивает заново, не
завершая команду с ошибкой.

Обе команды откажутся создать ВТОРОГО superadmin, если активный уже есть
(неважно, локальный он или через AD) — добавлять остальных администраторов
после этого нужно через `/admin/administrators`, войдя под первым.

## 12. Разделы `/admin`

- **Обзор** — состояние AD, последняя AD-синхронизация/обнаружение
  принтеров/запуск сборщика, счётчики, последние ошибки (из `sync_runs`).
- **Администраторы** *(только superadmin)* — найти пользователя в AD и
  назначить роль, ИЛИ создать нового ЛОКАЛЬНОГО пользователя (не требует
  AD) со случайным временным паролем — он показывается один раз сразу
  после создания (скопируйте и передайте пользователю лично, не по почте
  открытым текстом) и должен быть сменён при первом входе. `admin` может
  создавать локальных `viewer`/`admin`, но не `superadmin` — это может
  только superadmin (та же логика, что и для назначения ролей через AD).
  Отключить/удалить назначение — одинаково для локальных и AD-учёток.
  Никому не разрешено менять свою собственную роль; последнего активного
  superadmin нельзя понизить/отключить/удалить (система откажет с понятным
  сообщением) — независимо от того, локальный он или через AD.
- **Отделы** — CRUD; удаление отдела с привязанными пользователями/заданиями
  требует выбрать отдел для переназначения (либо просто снять "Активен" —
  архивирование без удаления).
- **Пользователи AD** — поиск и импорт из AD, назначение отдела (с флагом
  `lock`, см. ниже), локальное отключение, повторная синхронизация.
- **Группы AD** — поиск и импорт групп, синхронизация состава участников,
  правило "группа → отдел" (приоритет + активность).
- **Правила отделов (dry-run)** — показывает, что изменится при применении
  правил AD-группа→отдел, БЕЗ применения; кнопка "Применить" — отдельное
  действие. Конфликт (два правила с одинаковым наивысшим приоритетом на
  разные отделы) показывается явно, а не решается тихо.
- **Принтеры** — см. раздел 5.
- **Тарифы** — см. раздел 13.

### Ручное назначение отдела (`lock`)

На странице «Пользователи AD» назначение отдела с галкой **lock** защищает
его от автоматической AD-синхронизации: даже если пользователь состоит в
группе с правилом на другой отдел, синхронизация (раздел «Правила отделов»)
не тронет заблокированное назначение. Использовать для исключений
("этот сотрудник числится в отделе продаж по AD, но фактически работает в
бухгалтерии").

## 13. Тарифы (price_rules)

`/admin/pricing` — версионированные тарифы: цена за страницу, цвет/Ч/Б,
привязка к конкретной очереди (пусто = тариф по умолчанию для всех очередей
без более специфичного правила), период действия (`valid_from`/`valid_to`,
не обязателен), приоритет. Правило конкретной очереди всегда важнее общего
тарифа по умолчанию, даже при равном приоритете; несколько правил одной
очереди разруливаются по приоритету.

**Важно:** стоимость уже вставленных заданий печати НЕ пересчитывается при
изменении/отключении тарифа — новая цена действует только для новых
заданий. Это сделано намеренно (историческая стоимость должна быть
стабильной для бухгалтерии/отчётности задним числом).

Там же — тестовый расчёт: выбрать очередь и количество страниц, увидеть,
какой тариф сработает и какая будет итоговая стоимость, без создания
реального задания.

## 14. Аудит

Все административные действия (создание/изменение отделов, назначение
ролей, импорт AD-пользователей/групп, изменение тарифов, обнаружение
принтеров и т.д.) пишутся в таблицу `audit_log`: кто, когда, что, старое и
новое значение (без секретов — пароли/токены/cookie туда не попадают даже
случайно, см. `printaudit/audit.py`), IP-адрес. Смотреть можно любым
SQLite-клиентом:

```sql
SELECT created_at, action, object_type, object_id, old_value, new_value
FROM audit_log ORDER BY created_at DESC LIMIT 50;
```

Имя документа (`print_jobs.document_name`) может быть чувствительным —
настройка `document_name_policy` в `config.yaml` (`full`/`masked`/`none`)
управляет тем, что реально попадает в БД для новых заданий (см. комментарий
в `config/config.example.yaml`).

## 15. Резервное копирование

Для SQLite — просто скопировать файл БД (путь из `config.yaml` -> `db.url`)
при остановленном сборщике и веб-сервере (или принять небольшой риск копии
файла "на лету" — SQLite это обычно переживает, но чистая копия надёжнее).
Резервную копию `.env` хранить отдельно от кода (в менеджере паролей/сейфе
организации) — она содержит пароль сервисного AD-аккаунта и секрет сессий.

## 16. Миграции БД (Alembic)

Схема БД версионируется через Alembic (`alembic/versions/`). Применяются
автоматически при `python scripts\init_db.py`, либо вручную:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
```

Это безопасно как на пустой БД, так и на уже работающей — первая ревизия
(`90fa7d836021_baseline_existing_mvp_schema.py`) создаёт исходные 5 таблиц
MVP только если их ещё нет. Откат (`alembic downgrade`) для базовой ревизии
намеренно не реализован (это удалило бы накопленную историю печати) — для
отката восстанавливайте БД из резервной копии.

## 17. Тесты

```powershell
pip install -r requirements-dev.txt
python -m pytest tests/ -v
```

Ничего из этого не требует реального AD-домена, принтера или сети: AD
замокан через встроенный in-memory LDAP-сервер `ldap3` (MOCK_SYNC),
`Get-Printer`/`Export-PrintEvents.ps1` подменяются на уровне
`subprocess.run`/фабрик функций, у каждого теста своя временная SQLite БД.
Запускать после любых изменений в `printaudit/`, `webapp/`, `collector/`,
`alembic/` перед тем, как выкатывать на реальный сервер.

## 18. Журнал заданий печати (`/print-jobs`)

В отличие от агрегированных отчётов (по отделам/пользователям/принтерам),
`/print-jobs` — построчный журнал: дата/время, площадка, Print Server,
пользователь, отдел, принтер, документ (с учётом `document_name_policy` —
журнал не может показать то, что не было сохранено), компьютер-источник
(если удалось откалибровать `field_map.source_computer`), число страниц
(и, если откалиброваны копии — их количество), цвет (Цветная/Ч/б/не
определено), стоимость, ID задания.

Фильтры — период, площадка, Print Server, пользователь, отдел, принтер,
цвет, поиск по названию документа — все применяются на сервере (SQL
`WHERE`), сама таблица никогда не загружается в браузер целиком: список
постранично (`page`/`page_size`, по умолчанию 50, максимум 200 строк за
раз). Ссылки «журнал» на страницах «По пользователям»/«По принтерам»
открывают `/print-jobs` уже с подставленным фильтром и текущим периодом.

`/api/print-jobs` и `/export/csv` принимают те же фильтры и возвращают те
же поля (по одному общему списку колонок — см.
`webapp/main.py::_job_to_dict`). У API появился заголовок ответа
`X-Total-Count` с общим числом найденных заданий (сама форма ответа —
по-прежнему список объектов, для обратной совместимости с уже
существующими интеграциями).

## 19. Режимы приложения: standalone / agent / central

См. подробно [docs/MULTISITE_ARCHITECTURE.md](MULTISITE_ARCHITECTURE.md).
Коротко: `APP_MODE` в `.env` (по умолчанию `standalone` — прежнее
поведение без единого изменения). `agent` — площадка дополнительно
отправляет накопленные задания в центр через durable outbox
(`collector/agent_sync.py`, отдельная задача Task Scheduler). `central` —
принимает события от агентов и отдаёт общий веб-интерфейс по всем
площадкам, локально события не собирает.

## 20. Центральный менеджер Print Server (`/admin/print-servers`, `/admin/sites`)

Доступно admin/superadmin. `/admin/sites` — создать площадку (`site_code` +
название). `/admin/print-servers` — зарегистрировать Print Server на
площадке; при регистрации (и при последующей ротации) токен агента
показывается **один раз**, во flash-сообщении сразу после действия —
скопируйте его сразу в `AGENT_TOKEN` в `.env` агента, повторно посмотреть
его нельзя (в БД хранится только хэш).

Список показывает по каждому Print Server: площадку, вычисляемый статус
(`online`/`warning`/`offline`/`disabled`/`pending` — по возрасту
heartbeat, не хранится "навсегда" как поле), версию агента, время
последнего heartbeat/успешной синхронизации, сколько событий у агента
ещё не подтверждено (`pending_queue_size`, приходит с heartbeat), текст
последней ошибки, число активных принтеров и заданий за сегодня.
Действия: «Перевыпустить токен» (старый немедленно перестаёт работать),
«Отключить»/«Включить» (отключённый Print Server не может пройти
аутентификацию в `/api/v1/agent/*`, даже с правильным токеном).

Удалённое управление очередями/драйверами/службами Windows на Print
Server из этой страницы **не реализовано** — это регистрация, статус,
синхронизация и отчётность, не remote command execution (см. ограничения
в docs/MULTISITE_ARCHITECTURE.md, §9).

Данные разных площадок не смешиваются из-за одинаковых имён принтеров или
логинов — идемпотентность и уникальность очередей теперь строятся на
`print_server_id`, а не на голом имени/`site_code` (см. §4 того же
документа). Фильтр по площадке есть в дашборде, `/by-user`, `/by-printer`,
`/print-jobs`, `/api/print-jobs`, `/export/csv`.

## 21. Развёртывание агента на площадке

1. На сервере площадки — обычная установка (см. README, «Развёртывание на
   одном объекте»), включая калибровку `field_map` — она не отличается от
   standalone.
2. На центральном сервере, под admin/superadmin: `/admin/sites` → создать
   площадку (если ещё нет), `/admin/print-servers` → зарегистрировать этот
   Print Server, скопировать показанный один раз токен.
3. В `.env` агента добавить:
   ```
   APP_MODE=agent
   CENTRAL_BASE_URL=https://<центральный-сервер>
   AGENT_SITE_UUID=<из /admin/print-servers>
   AGENT_PRINT_SERVER_UUID=<из /admin/print-servers>
   AGENT_TOKEN=<показанный один раз токен>
   ```
4. Зарегистрировать задачу отправки в центр (отдельно от сборщика):
   ```powershell
   .\deploy\register_agent_sync_task.ps1
   ```
5. Проверить соединение с центром без ожидания реального цикла Task
   Scheduler:
   ```powershell
   .\.venv\Scripts\python.exe scripts\agent_diagnose.py
   ```
   Скрипт по шагам печатает `[OK]`/`[FAIL]`: конфигурация `.env`, DNS, TCP,
   TLS, и реальный вызов heartbeat — так видно, что именно не так, не
   только "не работает".
6. Запустить сборщик и задачу синхронизации, распечатать тестовый документ,
   через 1-2 минуты проверить `logs/collector.log` и `logs/agent_sync.log`,
   затем убедиться, что задание появилось в центральном `/print-jobs` с
   правильной площадкой/сервером.
