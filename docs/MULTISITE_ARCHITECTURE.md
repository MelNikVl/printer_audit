# Мультиплощадочная архитектура: журнал заданий, агенты, центр

Этот документ описывает архитектуру, добавленную в ветке
`feature/print-job-monitoring-multisite`: подробный журнал заданий печати
(`/print-jobs`) и основу централизованного сбора данных с нескольких
площадок/Print Server. Не переписывает существующий standalone-режим — его
поведение не изменилось, если вы просто продолжаете работать как раньше
(см. «Совместимость» в конце).

## 1. Три режима приложения (`APP_MODE`)

Задаётся в `.env` (не в `config.yaml` — это деплой-параметр, не свойство
площадки). По умолчанию — `standalone`.

| Режим | Что делает |
|---|---|
| `standalone` | Как раньше: коллектор читает Event 307 локально, пишет прямо в свою БД, веб-UI показывает только её. Работает без единой настройки центра. |
| `agent` | То же самое локальное чтение/запись, ПЛЮС каждое новое задание ставится в durable outbox и периодически отправляется в центр отдельным заданием (`collector/agent_sync.py`). |
| `central` | Не собирает события локально (обычно на этом сервере нет Print Server вообще) — принимает пакеты от агентов через `/api/v1/agent/*` и отдаёт общий веб-интерфейс/отчёты по всем площадкам. |

`agent` и `central` — это ОДИН И ТОТ ЖЕ код приложения, просто по-разному
настроенный и используемый; таблицы (`print_jobs`, `printer_queues`,
`sites`, `print_servers`, ...) одинаковы во всех трёх режимах.

**Fail-fast на опечатку.** Если `APP_MODE` вообще не задан — это
`standalone` (обратная совместимость). Но если `APP_MODE` ЗАДАН и не равен
ни одному из трёх значений (опечатка вроде `APP_MODE=centrall`) —
`printaudit.agent_settings.get_agent_settings()` бросает
`InvalidAppModeError` везде, где читается (веб-приложение отказывается
стартовать вообще, не только когда доходит до агентского API; `collector/
collect_print_events.py` и `collector/agent_sync.py` тоже падают явно).
Опечатка в production-конфигурации никогда не откатывает режим тихо на
`standalone`.

**`/api/v1/agent/*` доступен ТОЛЬКО в `APP_MODE=central`.** Роутер
подключён в `webapp/main.py` всегда (для простоты сборки приложения), но
оба endpoint'а (`require_central_mode`, первая проверка, ДО токена)
отвечают 404 в `standalone`/`agent` — как будто их вообще нет. Это значит:
развёрнутый в `agent`-режиме сервер не примет чужой батч, даже если кто-то
пришлёт валидный (например, украденный у другого агента) токен.

## 2. Поток данных

```
Площадка (Windows Print Server, APP_MODE=agent)
  Get-WinEvent (Event 307) -> collector/collect_print_events.py
      -> печатает в СВОЮ локальную БД (site_id/print_server_id
         авто-заведены из config.yaml — см. printaudit/sites.py)
      -> АТОМАРНО ставит OutboxEvent в ТОЙ ЖЕ транзакции
                    │
                    ▼
  collector/agent_sync.py (отдельная задача Task Scheduler, каждые 1-2 мин)
      -> исходящее HTTPS: POST /api/v1/agent/events/batch (bearer-токен)
      -> POST /api/v1/agent/heartbeat
                    │
                    │  (агент САМ инициирует соединение; входящих портов
                    │   на Print Server открывать не нужно, центр никогда
                    │   не подключается к площадке напрямую)
                    ▼
Центральный Print Audit (APP_MODE=central)
  webapp/agent_api.py -> проверяет токен -> вставляет PrintJob
      (идемпотентно по print_server_id+record_id)
                    │
                    ▼
  Общий веб-интерфейс: /print-jobs, /by-user, /by-printer, дашборд,
  /admin/print-servers — с фильтром по площадке везде.
```

## 3. Сущности

### Site
Площадка: стабильный `uuid`, уникальный `site_code`, название, активность.
Standalone/agent-коллектор сам заводит себе площадку (по `site_code` из
`config.yaml`) при первом запуске — ручная регистрация не нужна, если вам
не важен центр. Для центра площадку создаёт администратор в
`/admin/sites` (нужен `site_code`, остальное необязательно).

### PrintServer
Регистрация одного Print Server/агента на площадке: стабильный `uuid`,
имя Windows-сервера, отображаемое имя, версия агента/протокола,
`last_heartbeat_at`/`last_contact_at`/`last_sync_at`/`pending_queue_size`/
`failed_queue_size`/`last_error`/`last_ingest_error`,
`token_hash` (хэш bearer-токена — сырой токен никогда не хранится),
`is_disabled`. **Статус НЕ хранится** — вычисляется на каждый рендер
страницы по возрасту `last_heartbeat_at` (`printaudit/sites.py::compute_status`):

- `online` — heartbeat моложе 5 минут;
- `warning` — от 5 до 30 минут;
- `offline` — старше 30 минут;
- `disabled` — администратор отключил вручную (перекрывает всё остальное);
- `pending` — heartbeat вообще ещё не было.

Как и в standalone-режиме коллектор авто-заводит СВОЙ ЛОКАЛЬНЫЙ
`Site`+`PrintServer` (для внутренней идемпотентности БД) — это НЕ то же
самое, что `AGENT_SITE_UUID`/`AGENT_PRINT_SERVER_UUID` в `.env`, которыми
агент представляется ЦЕНТРУ. Локальная авто-регистрация не требует
токена (это просто строки в своей же БД); представление центру требует
токена, выданного администратором центра в `/admin/print-servers`.

**`last_contact_at` vs `last_sync_at` vs `last_error` vs `last_ingest_error`**
(pre-merge hardening — раньше `last_sync_at` ошибочно обновлялся на любой
успешный HTTP-ответ, даже если весь присланный пакет был отклонён):

| Поле | Когда обновляется | Кто пишет |
|---|---|---|
| `last_contact_at` | На КАЖДЫЙ успешно аутентифицированный запрос (batch ИЛИ heartbeat) — "агент достучался, токен верный" | `webapp/agent_api.py` |
| `last_sync_at` | ТОЛЬКО когда `/events/batch` обработан без единого `rejected` (inserted/duplicate — оба успех; пустой пакет тоже считается) | `webapp/agent_api.py` |
| `last_error` | Что САМ агент сообщил о себе через heartbeat (например, ошибка отправки на его стороне) | `collector/agent_sync.py` → heartbeat |
| `last_ingest_error` | Что ЦЕНТР обнаружил при разборе присланных событий (например, "отклонено 2 из 10") — очищается следующим полностью успешным пакетом | `webapp/agent_api.py` |

`last_error` и `last_ingest_error` — осознанно РАЗНЫЕ поля: одно не должно
затирать другое, это две независимые точки зрения (агента про себя, и
центра про присланные данные).

### OutboxEvent
Одна строка на каждое задание печати, ожидающее подтверждения доставки —
см. §5.

## 4. Исправленная идемпотентность (было — потенциальный баг)

**До этой ветки**: `print_jobs` были уникальны по `(site_code, record_id)`,
`printer_queues.printer_name` — уникально глобально. Оба варианта ломаются,
если на одной площадке два Print Server (у каждого свой независимый
счётчик `EventRecordID`) или два сервера/площадки называют очередь
одинаково ("HP-3F-BW" на двух объектах).

**Сейчас**: `print_jobs` уникальны по `(print_server_id, record_id)`,
`printer_queues` — по `(print_server_id, printer_name)`. Миграция
`80b73be83524` при обновлении существующей БД сама создаёт "унаследованный"
`PrintServer` (`LEGACY-<site_code>`) для каждого встреченного `site_code` и
переносит туда все существующие строки — история не теряется. Если в ОДНОЙ
БД исторически встретилось больше одного `site_code` (в этой архитектуре
такого не предполагалось до сих пор, но проверка есть), `printer_queues`
не может быть однозначно разнесена по серверам автоматически — миграция
печатает предупреждение в вывод `alembic upgrade`, `print_server_id`
остаётся `NULL` для этих строк, и стоит проверить `/admin/printers` вручную.

## 5. Гарантии доставки (Part 4)

`OutboxEvent.status` — три состояния, и переход между ними ОСОЗНАННО
асимметричен (pre-merge hardening; более ранняя версия ошибочно повторяла
даже терминально отклонённые события):

- **`pending`** — обычное/повторно-планируемое состояние: свежесозданная
  строка, строка после сетевого сбоя, или строка, для которой центр вернул
  200, но забыл включить её в `results` (нарушение протокола со стороны
  центра — не вина события, тоже просто retry).
- **`delivered`** — терминально, успех: ack `inserted` ИЛИ `duplicate` (оба
  означают "центр это принял", разница не важна агенту).
- **`failed`** — ТЕРМИНАЛЬНО, но НЕ успех: ack `rejected` (центр явно
  сказал "это невалидные данные"). `next_attempt_at` сбрасывается в `NULL`,
  и `_fetch_due_outbox_rows()` (фильтрует строго `status == "pending"`)
  больше никогда не вернёт эту строку автоматически — повторная
  автоматическая отправка заведомо невалидных данных не имеет смысла и
  только шумит в логах. Единственный путь вернуть её в оборот — осознанный
  ручной `python collector\agent_sync.py --retry-failed` ПОСЛЕ того, как
  причина отклонения устранена (см. `collector/agent_sync.py::retry_failed_rows`).

Остальные гарантии:

- **Атомарность**: `PrintJob` и `OutboxEvent` создаются в одной транзакции
  (`collect_print_events.py`, `session.add(job); session.add(OutboxEvent(print_job=job))`,
  один `session.commit()`) — восстановление после сбоя между вставкой и
  отправкой не может «потерять» задание, потому что отправка узнаёт о нём
  из той же строки БД, что и сама вставка.
- **Устойчивость к перезапуску**: очередь — это таблица в БД, а не память
  процесса; после перезапуска агента `collector/agent_sync.py` просто
  видит те же `pending`-строки.
- **Пакетная отправка**: до `agent.max_batch_size` (по умолчанию 500,
  локальный лимит агента) событий за один HTTP-запрос — центр НЕЗАВИСИМО
  дополнительно ограничивает это своим `MAX_EVENTS_PER_BATCH` (см. §5а
  ниже), не доверяя настройке конкретного агента.
- **Идемпотентность повторной отправки**: приём на центре ищет
  существующую строку по `(print_server_id, record_id)` — повторная
  отправка того же пакета или частично повторяющегося пакета не создаёт
  дублей, "уже было" помечается `duplicate`, не ошибкой.
- **`pending_queue_size`/`failed_queue_size`** передаются в heartbeat
  РАЗДЕЛЬНО (и хранятся раздельно в `PrintServer`, и показываются раздельно
  в `/admin/print-servers`) — `pending_queue_size` НЕ включает терминально
  отклонённые: "сколько ещё реально досошлётся само" и "сколько зависло и
  ждёт ручного вмешательства" — разные вопросы, смешивать их в одно число
  вводило бы в заблуждение.
- **Backoff**: при сетевом сбое/недоступности центра — экспоненциальная
  задержка (30с базово, максимум 30 минут) со случайным джиттером
  (±30%), пересчитывается на каждую неудачную попытку
  (`collector/agent_sync.py::compute_backoff_seconds`).
- **Изоляция от сборщика**: `agent_sync.py` — ОТДЕЛЬНАЯ задача Task
  Scheduler от `collect_print_events.py`. Недоступность центра не
  тормозит и не останавливает локальный сбор событий печати — они просто
  копятся в outbox до восстановления связи.
- **Ничего не удаляется**: доставленные строки `OutboxEvent` остаются в
  таблице навсегда как локальная история (не то же самое, что удаление
  `print_jobs` — те не удаляются никогда и никем).

## 6. Токены агента

- MVP: один секретный bearer-токен на каждый `PrintServer`
  (`printaudit/security/agent_tokens.py`), генерируется
  `secrets.token_urlsafe(32)`.
- Показывается администратору РОВНО ОДИН РАЗ — во flash-сообщении сразу
  после создания регистрации или ротации (`/admin/print-servers`), никогда
  не хранится в открытом виде и не попадает в `audit_log` (там сохраняется
  только факт действия, не сам токен) и ни в один лог.
- В БД — только `sha256(токен)` (`PrintServer.token_hash`); проверка —
  прямой запрос по хэшу (тот же принцип, что и `WebSession.id` — хэш
  случайного токена, а не сам токен), константное сравнение не требуется
  дополнительно, так как поиск идёт по значению хэша через индекс, а не
  через побайтовое сравнение хэшей в коде.
- Отзыв/ротация — немедленны: старый токен просто не совпадает ни с одной
  строкой `token_hash` после замены/при `is_disabled=True`.
- Все запросы предполагают HTTPS — `AGENT_REQUIRE_HTTPS=true` (по
  умолчанию) в API отклоняет запрос, если он пришёл не по HTTPS.
- mTLS в эту версию не входит намеренно (MVP), но архитектура (отдельная
  функция аутентификации `require_agent_print_server`, не завязанная на
  конкретный механизм) позволяет добавить его позже без переделки схемы.

### HTTPS за реверс-прокси (nginx/IIS/...)

Если TLS завершается на реверс-прокси, а до `uvicorn` запрос доходит уже
как обычный HTTP, `request.url.scheme` внутри приложения ВСЕГДА будет
`"http"` — слепая проверка `if request.url.scheme != "https"` либо
ошибочно блокирует легитимный трафик агентов, либо её приходится
выключать (`AGENT_REQUIRE_HTTPS=false`), теряя реальную защиту насовсем.

Решение — `webapp/middleware.py::TrustedProxyHeadersMiddleware`: доверяет
заголовку `X-Forwarded-Proto` ТОЛЬКО если непосредственный TCP-peer (тот,
кто реально подключился к `uvicorn` — сам прокси, не конечный клиент)
входит в `TRUSTED_PROXY_IPS` (`.env`, список IP через запятую). Пустой/не
заданный список (по умолчанию) — заголовок полностью игнорируется, и
прямое (без прокси) соединение обязано реально быть HTTPS. Если peer НЕ
в списке — заголовок тоже полностью игнорируется: иначе любой внешний
клиент мог бы сам прислать `X-Forwarded-Proto: https` и обойти
`AGENT_REQUIRE_HTTPS`. См. `.env.example` за примерами правильной/
неправильной настройки.

Дополнительно (необязательно, второй слой той же защиты) — встроенные
флаги uvicorn `--proxy-headers --forwarded-allow-ips=<IP прокси>`
(`deploy/run_webapp.ps1 -ForwardedAllowIps`) переписывают
`scope["scheme"]` ещё до того, как ASGI-приложение вообще его увидит; они
не заменяют `TRUSTED_PROXY_IPS` (и не тестируются через FastAPI
TestClient, в отличие от `TrustedProxyHeadersMiddleware`), а дополняют.

## 6а. protocol_version

Оба endpoint'а (`/events/batch`, `/heartbeat`) сверяют присланный
`protocol_version` с `printaudit.agent_settings.PROTOCOL_VERSION` (сейчас
`1`) ДО какой-либо записи в БД. Несовпадение — `400` со структурированным
(машинно-читаемым) телом:

```json
{"detail": {"error": "unsupported_protocol_version", "supported_protocol_version": 1, "received_protocol_version": 2}}
```

Это не временный сбой — агенту со старым/новым протоколом нужно
обновление, а не бесконечный retry с backoff; структурированный `error`
позволяет агенту (в будущем) отличить этот случай от прочих 4xx
программно, а не парсингом текста сообщения.

## 6б. Лимиты входящего пакета (центральный сервер)

Центр не доверяет ЛЮБОМУ присланному агентом числу/строке — лимиты
проверяются независимо от того, что агент сам о себе думает (см.
`webapp/agent_api.py`, константы в начале файла):

| Что | Лимит | Почему |
|---|---|---|
| Событий в пакете | 1000 (`MAX_EVENTS_PER_BATCH`) | не зависит от `agent.max_batch_size` конкретного агента — центр защищает себя сам |
| Тело запроса | 5 МБ (`MAX_BODY_BYTES`) | проверяется ДО разбора JSON — `MaxBodySizeMiddleware`, только для префикса `/api/v1/agent` |
| `user_name`/`user_login_normalized` | 200 симв. | = ширина колонки `PrintJob.user_name`/`.user_login_normalized` |
| `printer_name` | 200 симв. | = ширина `PrintJob.printer_name` |
| `document_name` | 500 симв. | = ширина `PrintJob.document_name` |
| `source_computer` | 200 симв. | = ширина `PrintJob.source_computer` |
| `department_name` | 200 симв. | = ширина `Department.name` |
| `last_error` (heartbeat) | 2000 симв. | как `SyncRun.error_message` |
| `record_id` | 0..2 147 483 647 | укладывается в 32-битный `INTEGER` PostgreSQL (SQLite сам по себе не ограничивает — вышли бы за диапазон только на проде) |
| `total_pages` | 0..1 000 000 | разумный верхний предел |
| `copies` | 1..100 000 | |
| `pages_per_copy` | 0..1 000 000 | |
| `price_per_page`/`cost` | 0..верхний предел, конечное число | см. ниже |

Без этих лимитов превышающая ширину колонки строка тихо обрежется на
SQLite, но упадёт с ошибкой на PostgreSQL уже после прохождения
бизнес-логики — лимиты ловят это на входе, единообразно для обоих бэкендов.

**NaN/Infinity/отрицательные деньги.** Стандартный `json.loads` (в отличие
от строгого JSON) допускает литералы `NaN`/`Infinity`/`-Infinity` как
Python-расширение — если агент (или кто-то, подделавший его токен) их
пришлёт, `price_per_page`/`cost` отклоняются явной проверкой
(`_reject_non_finite`) с понятным сообщением, а не тихо проходят как
`float('nan')` в БД/отчёты.

**Структурные нарушения отклоняют ВЕСЬ пакет, не одно событие.** Если хотя
бы одно событие в пакете не проходит схему (диапазон/длина/NaN/Infinity/
неверный `color_source`), pydantic отклоняет запрос целиком (`422`) ДО
какой-либо записи в БД — ни одно событие пакета, включая структурно
валидные, не пишется частично. Это отличается от "мягкого" отклонения по
бизнес-причине (пример: `printer_name` из одних пробелов, `time_created` в
нераспознаваемом формате, дубликат `record_id`) — такие проверяются УЖЕ
внутри цикла по событиям, в собственном `SAVEPOINT` на событие, и не
валят остальные события того же пакета (см. §5).

## 7. Поведение при потере сети

- Разрыв связи агент → центр: локальный сбор продолжается без изменений;
  `agent_sync.py` копит ошибки в `OutboxEvent.last_error`, не падает,
  Task Scheduler видит нормальное завершение процесса (код 0) даже когда
  отправка не удалась — это ожидаемое временное состояние, не сбой задачи.
- Восстановление связи: следующий запланированный запуск `agent_sync.py`
  просто видит те же необработанные строки (проверяет `next_attempt_at`)
  и отправляет их — без ручных действий.
- Разрыв связи центр → агент (например, злоумышленник или сетевой сбой
  блокирует именно ответы) не рассматривается отдельно — с точки зрения
  агента это тот же случай "не получили успешный ответ", обрабатывается
  тем же backoff-механизмом.

## 8. total_pages, копии и цвет — что реально известно

**Исследовано специально для этой ветки**: до сих пор проект НИКОГДА не
проверял и не документировал, означает ли `total_pages` (Event 307,
позиционное свойство, калибруется через `field_map`) итоговое число
отпечатанных листов ВКЛЮЧАЯ все копии, или число страниц на одну копию.
Ни код, ни `docs/ADMIN_GUIDE.md`, ни `docs/RESEARCH.md` до этой ветки не
делали никакого заявления на этот счёт — калибровка всегда была только про
"какой индекс `Properties[i]` брать", а не про семантику самого числа.

**Решение в этой ветке**: не гадать. `total_pages` продолжает передаваться
как есть — прежнее поведение, прежние тарифы/отчёты не меняются. Отдельно
добавлены nullable `copies`/`pages_per_copy` в `print_jobs` и
соответствующие ОПЦИОНАЛЬНЫЕ ключи `field_map.copies`/`field_map.pages_per_copy`
(см. `config/config.example.yaml`) — если на конкретном сервере при
калибровке (`collector/calibrate_event_fields.ps1`) находится надёжный
индекс для числа копий и страниц-на-копию, администратор может указать
эти индексы, и коллектор начнёт заполнять эти поля (при отсутствии —
остаются `NULL`, никаких выдуманных значений). Существующие записи не
затрагиваются и не требуют backfill.

**Цвет**: аналогично, Event 307 в этом проекте не сообщает цвет документа
(подтверждено в `docs/RESEARCH.md` ранее, не изменилось). Раньше
неизвестный цвет молча становился `is_color=False` — это было неверно
("неизвестно" ≠ "точно чёрно-белая") и исправлено: `is_color` теперь
tri-state (`True`/`False`/`None`), `color_source` объясняет источник
(`queue` — явная настройка очереди/тарифа/правила; `event` — из самого
события, зарезервировано на будущее и для центрального API, если
какой-то агент однажды будет получать более точные данные; `unknown` —
достоверно не определено). Для БИЛЛИНГА при `unknown` всё равно
консервативно берётся Ч/Б-тариф (дешевле, чем ошибочно посчитать как
цветную) — но это решение о цене, а не заявление о фактической
цветности; журнал/отчёты показывают "не определено", а не "Ч/б"
(см. `printaudit/printers/resolver.py::resolve_price`,
`tests/test_pricing_v2.py`).

## 9. Ограничения этого MVP

- mTLS не реализован (только bearer-токен + обязательный HTTPS).
- Central API аутентифицирует агента, но не проверяет, что конкретный
  IP/подсеть ожидаемы — это отдаётся на уровень сетевой инфраструктуры/
  файрвола/реверс-прокси заказчика.
- Удалённое управление очередями/драйверами/службами Windows на
  Print Server из центра НЕ реализовано (и не планировалось в этом
  этапе) — `/admin/print-servers` — это регистрация, статус, синхронизация
  и отчётность, не remote command execution. Структура (bearer-токен на
  сервер, отдельный versioned API) допускает добавить позже безопасную,
  явно согласованную доставку КОНФИГУРАЦИИ агенту (например, обновлённый
  `field_map` или интервал синхронизации) тем же путём, но это не входит
  в эту ветку.
- `Department` остаются глобальными (не привязаны к площадке) — если
  разным площадкам когда-нибудь потребуются полностью раздельные списки
  отделов с одинаковыми названиями, это отдельная задача на будущее.
- Автоматическое сопоставление `printer_queues` при неоднозначном
  legacy-backfill (несколько `site_code` в одной исторической БД) требует
  ручной проверки — см. §4.
- `collector_state` (курсор чтения журнала событий) остаётся per-`site_code`,
  не per-`print_server_id` — это осознанно: сам процесс коллектора всегда
  работает с ОДНИМ локальным журналом событий одного физического сервера,
  случай "два коллектора на одной площадке" означает два ОТДЕЛЬНЫХ
  локальных процесса/БД, а не общий курсор — коллизий не возникает.

## 10. Дальнейшее развитие

- Полноценный remote-config push агентам (следующий `protocol_version`).
- mTLS как альтернатива/дополнение к bearer-токену.
- Более точное определение цвета через разбор EMF-спула или
  SNMP/WMI-счётчики принтера (см. `docs/ROADMAP.md`, пункт 2 — не входил
  в объём этой ветки и остаётся отдельной задачей).
- Полноценный remote print-server manager: обновление драйверов, служб,
  очередей централизованно (явно вынесено за рамки этого MVP по
  соображениям безопасности — произвольное remote command execution не
  реализовывалось намеренно).
- Пер-площадочные `Department`, если это станет реальной потребностью.
